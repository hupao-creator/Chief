# Published dispatch configuration

Each workspace in a Chief profile owns one collection in its SQLite store. Each registered
Harness owns discovery for its ordinary task defaults. Onboarding, workspace
prefetch, manual refresh and adapter invalidations request updates. The ordinary
settings panel reads the published presentation. Chief reads the options for the
selected, enabled targets from one immutable store snapshot. Thread editors,
Chief's own execution profile, and independent background-role profiles retain
their destination-specific settings and permission contracts.

A publication has a settings presentation, public routing options, and optional
Artificial Analysis model identities. The persisted projection admits named
public fields. Native request bodies, authentication headers and raw accounts
stay inside the adapter. A settings read after restart can recover the last
publication without launching the CLI. An existing installation with no publication
starts with the next provider update. No settings or Thread history migration is
required. In a headless profile, per-provider workers check installed Harnesses on startup and every five minutes.

Updates for a provider and source share acquisition. Cancelling a reader releases
its interest. A replacement source fences older work, and the write transaction
checks the saved source. A successful empty model array clears visible choices.
An unavailable or malformed observation preserves the last publication. Each
adapter identifies usable observations with its own native protocol. For example,
an OpenCode preliminary result can expose models before its account check settles.

Subscribers receive an initial wake and coalesced change notifications. Only
changes to projected routing choices wake Chief. Settings clients observe the
presentation digest on the normal Runtime state stream. Both read current data
on receipt. A stable projection has no write or notification. Model ordering is preserved in Settings and normalized by provider and model ID for routing. Native discovery
keys and retry policy are private to each adapter.

## Verification

**PBT-DISPATCH-PUBLICATION** generates two-provider traces of successful,
unchanged, empty, failed, superseded and recovered SQLite publications. The
oracle tracks public membership and notifications, checks restart isolation
and checks that a private native field cannot enter the stored view.

**PBT-DISPATCH-OPTIONS** passes generated unpublished model identifiers to all
four production adapters with discovery offline. It checks that native selectors
survive conversion, launch overrides are rejected and no provider lookup runs.
This boundary exercises wire conversion. Real account acceptance requires native
execution evidence. [Property inventory](../../../tools/verification/pbt/README.md)
